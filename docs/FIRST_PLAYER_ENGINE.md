# 先手必胜引擎设计

本文记录 `first-player-win` 引擎的目标、决策流程、正确性边界与验证方法。

## 1. 目标与规则前提

本版本的人机模式被固定为：

- **AI 执黑，永远先手**；玩家执白后行。
- 15 × 15 棋盘，横、竖、斜任意方向五子或更多即胜。
- **无禁手**：没有三三、四四、长连禁手。先手可以自由构筑双活三、四三、双四等复合威胁。

五子棋先手必胜不是本项目的臆测。Allis 等人在 1994 年用威胁空间搜索与大规模计算证明了
无禁手 15×15 五子棋的黑胜；其完整证明树约有十余万局面、35 层深，需要百万级 CPU 秒。
它不是一个可以手工写进前端的短开局谱。

因此本引擎的目标是**在应用可承受的思考时间内执行先手优势**：

1. 找到可证明的 VCF 杀棋时，给出真正的强制胜；
2. 找不到强制杀时，用深度搜索与棋型评估持续制造双威胁；
3. 对对手的成五、活四、活三与反杀保持战术警觉。

它不携带完整数学证明树，也不声称在任意完美防守下都能在有限时间内给出形式化证明。

## 2. 代码结构

```text
src/main/ai/engines/first-player/
├── engine.ts     # AIEngine 实现、根节点、迭代加深 α-β、时间控制
├── position.ts   # 棋盘状态、候选点、棋型分析、增量整线评估
├── vcf.ts        # VCF（连续冲四）强制搜索
└── index.ts      # 导出
```

人机模式只注册这个引擎（见 [`registry.ts`](../src/main/ai/registry.ts)）。渲染层在
[`useGomokuGame.ts`](../src/renderer/src/composables/useGomokuGame.ts) 中把 AI 固定为
`BLACK`、玩家固定为 `WHITE`，每次新局都由黑棋先落子。

## 3. 单步决策流水线

`chooseMove(request)` 按以下顺序工作：

1. **空盘**：天元 `H8` 开局。
2. **一步成五**：任意能立即连五的点直接落子。
3. **一步必败**：若对手存在成五点，必须封堵；有多处则只能选择其中最有反击价值的点。
4. **活四制造点抢占**：对手若存在“落子后形成活四”的点，下一手将出现两个无法同时封堵的
   成五点。这样的点必须在搜索前作为紧急防守点处理，而不是只靠评分排序。
5. **VCF 算杀**：只走冲四，寻找可证明的连续四杀。
6. **迭代加深 α-β**：从深度 2 开始逐层加深，直到深度上限或时间上限。
7. **兜底**：返回启发式评分最高的合法点。

所有合法性和不可变性由 `Position` 的 `analyze / place / undo` 保证，传入的
`request.board` 不会被修改。

## 4. VCF 为什么是可靠的

VCF 层只考虑两类攻方着法：

- 立即成五；
- 形成“冲四”的着法（落子后存在一个或两个可成五的完成点）。

对每个冲四：

- 若存在 **两个不同的完成点**（活四），防方无法同时封堵，攻方下一手必胜；
- 若只有一个完成点，防方唯一不输的应手就是占据该点；
- 如果防方自己存在任何即时成五点，攻方这个冲四就是假威胁——防方会直接成五，因此整条分支作废；
- 防方封堵后若自己也形成四或活四，递归中会再次检查防方的即时成五点，避免“反冲四”误判。

因此 VCF 返回的线路不是启发式猜测，而是“找到即必胜”的强制序列。递归有深度、节点数与时间
上限；搜索在副本式 `place/undo` 上进行，无论成功、超时还是中止，都会把棋盘恢复到进入 VCF
前的状态。

VCT（把活三也纳入连续威胁）更完整，但必须枚举防方对活三的所有应手，尤其是防方反冲四；
如果没有完整的反杀规则，很容易把“假必胜”当成胜利。因此本版本只把 VCF 结果视为可证明胜，
其余局面交给 α-β。

## 5. 评估与排序

候选点评分采用两层棋型信息：

- `analyze(index, stone)`：以假想落点为中心，检查四个方向的五格窗口，统计成五、完成点、
  活三窗口数，并给出进攻/防守分；
- 整线增量评估：每次落子/撤子只重算经过该点的四条线；每条线按最强棋型归类为
  活四、冲四、活三、眠三、活二等，使活四与普通四、活三与眠三在叶子评估中明显区分。

排序大致为：

```text
进攻棋型分 + 防守棋型分 × 1.02 + 天元距离奖励
```

防守权重略高于进攻，避免先手在追击时被对手反杀。对手活四制造点额外获得紧急加权；
活三制造点即使落在常规候选宽度之外，也会被补入候选，防止搜索漏算。

## 6. 强制延伸与搜索宽度

- 冲四或活三着法会把搜索延伸一层，避免威胁刚好落在视野之外。
- 根节点最多考察 18 个候选，浅层 12 个，深层逐步收窄到 6–8 个。
- 对手有唯一成五点或活四威胁时，候选会被收窄到“封堵 + 己方冲四”的紧急集合。
- 默认单步思考 2 秒，VCF 占其中最多 0.6 秒；α-β 有硬 deadline，随时可以中止并返回上一层
  完整深度的结果。

## 7. 验证

### 7.1 自动化测试

`pnpm test` 包含 [`tests/first-player.test.ts`](../tests/first-player.test.ts)：

- 固定执黑、天元开局；
- 一步成五与唯一成五点封堵；
- 合法落点、不可变性、AbortSignal、未知难度、满盘异常；
- 对经典启发式防守者的完整对局黑胜；
- 白棋首手贴近天元（正交相邻）与远离天元（角落）时黑胜。

### 7.2 35 个首手对称轨道压力测试

在白棋首手任意落子的 224 个点中，按中心 8 重对称（D4）可以归并为 35 个轨道。开发期用
一个独立脚本对每个轨道做黑（先手引擎）对白（同一引擎的强防守）自对弈：

- 双方各 300 ms：35 局中 33 局黑胜，2 局被白反杀。
- 黑 800 ms、白 300 ms：35 局中 32 局黑胜，3 局被白反杀。
- 黑默认 2 000 ms、白 300 ms：对上一组被反杀的三个首手 `[2,5]`、`[3,7]`、`[5,6]`
  复测，分别在第 19、17、43 手黑胜。

这组数据说明：思考预算对先手攻杀质量非常敏感。默认 2 秒预算下，先前失败的困难首手均被
黑棋反杀；但仍是**经验验证**，不是数学证明。真正需要在所有防守下都形式化必胜，需要引入
完整威胁空间证明树或更强的 VCT/Gomocup 级引擎。

### 7.3 界面联调

开发时通过 Electron 的 DevTools Protocol 实际启动打包后的应用并检查 DOM：

- 首屏只有一颗黑棋，手数为 01，状态为「轮到你落子」；
- 设置面板显示「AI · 黑棋 / 固定先手」，玩家为「你 · 白棋」；
- 点击 `I8` 后，白棋落下、AI 立即应手，手数变 03，轮次回到玩家。

## 8. 调参与后续方向

`FirstPlayerAI` 构造函数支持 `timeLimitMs / vcfTimeMs / maxDepth / rootWidth`，便于测试或按
设备性能调参。后续可以：

- 把搜索移入 `worker_threads` / `utilityProcess`，彻底消除主进程思考时的窗口控制卡顿；
- 增加带反杀规则的保守 VCT；
- 加入 Zobrist 置换表、杀手/历史启发与 PVS；
- 用更强的外部引擎生成一个小型开局库，并把它作为排序 tie-break，而不是完整证明。
